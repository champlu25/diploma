# Конституция разработки CRM системы для автоматизации деятельности лизингового брокера

Версия: 1.4  
Дата: 2026-04-21

## 1. Стек технологий

- Бэкенд: `Node.js + Express`
- База данных: `PostgreSQL`
- Фронтенд: `React + TypeScript + Vite + SCSS Modules + React Router Data Mode`

## 2. Правила взаимодействия в чате

- Перед реализацией я даю короткий план шагов.
- Если требования неоднозначны или есть риск ошибки, я задаю уточняющие вопросы до начала реализации.
- По ходу задачи я сообщаю прогресс короткими статусами.
- После выполнения я кратко фиксирую что сделано.
- За один запрос вносим небольшой объем кода и реализуем изменения маленькими последовательными шагами.
- Служебные сообщения для разработчика в проекте (логи, технические ошибки и диагностические ответы API) пишем на русском языке.

## 3. Правила написания кода фронтенда

- Для глобальных стилей используется отдельная папка `styles`.
- В папке `styles` должны быть файлы: `fonts.scss`, `globals.scss`, `variables.scss`, `reset.scss`, `index.scss`.
- Файл `styles/index.scss` является точкой входа для подключения глобальных стилей.
- В `styles/index.scss` `reset.scss` импортируется первым.
- В `variables.scss` в первую очередь выносятся: `fonts`, `colors`, `radius`, `spacing`.
- Другие значения выносим в переменные только при реальной повторяемости в проекте.
- Адаптивность на текущем этапе делаем за счет гибкой верстки (например, `flex`), отдельные брейкпоинты и мобильная версия сейчас не требуются.
- Инлайн-стили не используем, кроме крайней необходимости
- Не использовать шаблонный ИИ-дизайн; интерфейс должен выглядеть как ручная реализация по макету дизайнера.
- Для условного объединения CSS-классов используем `clsx`.
- HTTP-запросы выполняем через `axios`; компоненты не делают прямые запросы, запросы выносятся в слой API/сервисов.
- Компоненты не содержат бизнес-логику; бизнес-логику выносим в отдельные хуки, сервисы и утилиты.
- Использование типа `any` запрещено.
- JWT-токен хранить в httpOnly cookie

## 4. Правила проектирования БД

- Каждая таблица имеет первичный ключ id BIGINT GENERATED ALWAYS AS IDENTITY.
- Таблицы нормализуются до 3NF, если это не усложняет структуру без необходимости.
- Доменные сущности и классификаторы (роли, статусы, типы) выносятся в отдельные справочники и используются через внешние ключи.
- Связи многие-ко-многим реализуются через промежуточные таблицы.
- Все внешние ключи явно задаются через REFERENCES
- Используется только TIMESTAMPTZ, каждая таблица содержит created_at и updated_at типа TIMESTAMPTZ NOT NULL.
- Поля по умолчанию объявляются NOT NULL, если отсутствие значения не имеет бизнес-смысла.
- Денежные значения хранятся в NUMERIC или BIGINT (в минимальных единицах).
- Запрещено добавлять колонки, которые не используются в текущем релизе. Поле включается в схему базы данных только при наличии подтверждённого бизнес-требования или реального сценария чтения или записи в коде на текущем этапе разработки.
